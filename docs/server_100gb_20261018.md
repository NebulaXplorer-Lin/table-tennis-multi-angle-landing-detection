# 100GB磁盘训练迁移方案

日期 2026年10月18日

服务器磁盘为100GB总容量，采用原视频按需解码，不迁移233GiB的RGB帧库，也不生成Global缩放图像或Local裁剪图像的磁盘缓存。标签、划分、原帧号和真实PTS保持原有口径。旧267GiB迁移包的数据清单不适用于这台机器。

## 1 磁盘预算

原视频、标签和数据描述合计约33.74GiB。PP部分约0.78GiB，可先上传并开始球定位；TTGames部分约32.96GiB，事件阶段前再补齐。准确数值以新迁移包manifest.json为准。

| 项目 | 预算 |
| --- | --- |
| 原视频、标签与数据描述 | 约34GiB |
| 代码、5个参考权重与视频索引 | 小于0.2GiB |
| 冻结事件阶段必要的特征文件 | 先限制在2GiB内 |
| 新训练best、last、恢复状态和日志 | 预留4GiB |
| 错误索引、叠图视频与预测 | 预留3GiB |
| 导出与临时文件 | 预留3GiB |

项目按约46GiB上限排期，另给系统镜像和运行留空间。100GB十进制总容量约93GiB，不能当作100GiB可用。上传全数据前查看df -h的实际可用量，建议至少留出50GiB可用空间容纳数据和运行余量；如实际余量更少，应进一步按比赛视频分批处理，不能先上传再靠删系统文件腾空间。

“关闭缓存”在这里指关闭磁盘图像缓存。视频解码仍保留有上限的内存帧和解码器，Dataset也有有限内存LRU；不会把整段1080p视频常驻内存。事件阶段冻结后保存的小型描述符是训练输入，远小于原分辨率RGB缓存，训练前核对其实际体积。

## 2 新增的读取方式

[video_store.py](../ttnet/src/data_tools/video_store.py)从现有数据描述生成小型索引，FrameStore按记录PTS在原MP4上定位。每次seek回到前面的关键帧，再解码到目标PTS，不使用“帧号除以fps”猜测VFR时刻，也不把稀疏TTGames数组序号当成原视频帧号。PyAV的seek行为见[官方接口说明](https://pyav.org/docs/stable/api/container.html#av.container.input.InputContainer.seek)。

PP沿用原PNG准备路径的BGR到RGB像素。TTGames历史输入先存JPEG95再读取，因此新读取路径也重现这一步，避免直接换成视频原始RGB而静默改变输入。本机覆盖全部154个PP视频和12个TTGames视频、每视频首中尾合计498帧的抽查均与原NPY逐像素相同，结果见out/results/20261018_video_backend/audit.json。该抽查不等于逐帧穷举，比赛镜像仍需检查解码一致性。

每个FrameStore最多保留2个解码器，每个解码器最多8个已转换帧；Dataset的内存LRU另计。解码器在worker间重新创建，不共享打开的解码状态。解码库版本、像素处理代码和视频后端身份进入新特征缓存身份；源视频尺寸或PTS不匹配直接报错，不用最近帧补齐。

本机原始标签和NPY库没有被切换或删除。--publish仅用于服务器，将数据描述的frame_store.json指向视频索引，首次保留frame_store.before_video.json；视频、标签和split文件不改写。

## 3 使用新的迁移包

使用out/migration/20261018_server_100gb中的文件：

- code.tar.gz与reference_weights.tar.gz：当前源码和原始参考权重。
- data_stage1.files0：PP原视频、标签和描述；不含解码帧库。
- data_stage2.files0：TTGames原视频和描述；不含解码帧库。
- data.files0：上述两部分的合集。
- manifest.json与SHA256SUMS：大小及小包校验。

打包可重新执行，不覆盖已有目录：

```bash
python3 scripts/package_server_transfer.py --profile source-video
```

沿用[迁移说明](server_migration_20261018.md)中的小包上传、解压和验证方法，将原示例路径20261018_server_transfer全部改为20261018_server_100gb。服务器工作目录示例仍为/workspace/pingpong，SSH别名仍为train-server；按实际服务器替换。

先从本地传PP部分：

```bash
cd /home/radno/projects/pingpong
rsync -rt --partial --info=progress2 \
  --from0 --files-from=out/migration/20261018_server_100gb/data_stage1.files0 \
  ./ train-server:/workspace/pingpong/
```

## 4 在服务器建立视频索引

进入正确的比赛镜像环境后执行，不能直接使用本机uv.lock升级比赛依赖：

```bash
cd /workspace/pingpong
python3 -m ttnet.data_tools.video_store \
  --dataset data/datasets/pp_ball_v2 --publish
python3 -m ttnet.data_tools.video_store \
  --dataset data/datasets/pp_ball_events_v1 --publish
python3 -m ttnet.cli data verify --dataset data/datasets/pp_ball_v2 --full
```

这些命令只生成小型manifest与索引数组，不导出PNG、JPEG或原始RGB。--full校验源视频SHA256，并抽查每视频首、中、尾的真实索引帧。PP球定位预期仍为154视频、23690帧。

球定位使用新配置，磁盘图像缓存已明确关闭，workers从2起步：

```bash
python3 -m ttnet.cli train \
  --config configs/server/ball_compact.json --stage global --dry-run
```

确认环境、坐标和配置后先做smoke，再启动正式训练。Local仍需显式传对应Global checkpoint：

```bash
python3 -m ttnet.cli train \
  --config configs/server/ball_compact.json --stage global --smoke

python3 -m ttnet.cli train \
  --config configs/server/ball_compact.json --stage local \
  --global-checkpoint /workspace/pingpong/out/experiments/YOUR_GLOBAL_RUN/checkpoints/best.pt \
  --dry-run
```

YOUR_GLOBAL_RUN为实际新Global运行目录；若复用参考定位器则保持Global和Local成对。当前三个训练入口的GradScaler已调整为torch 2.1支持的torch.cuda.amp接口，但仍须在真实比赛镜像完成GPU前后向和恢复预检；本地通过不等于4090上已测。

## 5 事件阶段补齐TTGames

从本地传第二批：

```bash
rsync -rt --partial --info=progress2 \
  --from0 --files-from=out/migration/20261018_server_100gb/data_stage2.files0 \
  ./ train-server:/workspace/pingpong/
```

传完后在服务器执行：

```bash
cd /workspace/pingpong
python3 -m ttnet.data_tools.video_store \
  --dataset data/datasets/openttgames_event25_v3 --publish
python3 -m ttnet.cli data verify \
  --dataset data/datasets/openttgames_event25_v3 --full
python3 -m ttnet.cli train \
  --config configs/server/event_reference.json --dry-run
```

TTGames预期仍为12视频、28883个已准备帧索引。历史metadata中的本机绝对视频路径在视频后端下重定位到当前数据目录，原路径保留为来源信息。连续关联从源视频流式运行，并仅保留需要的描述符，不为长比赛生成整段RGB帧库。旧的dense context导出在此后端直接拒绝执行，避免无意写满磁盘。

event_reference只是现有旧桌框TCN的检查基线。独立单帧桌框分支与新融合尚需按白皮书实现；它们也应从原图解码后在线变换，不能为了省空间预缩原视频或改变小球像素尺度。少量FT仍在线计算可求导特征，不把冻结描述符误用成可更新图像路径。

## 6 速度与产物管理

此方案节约空间，会增加随机取帧、seek和CPU解码成本。此前6–13小时基于已有RGB帧库，不能直接用于本方案。上机在真实无磁盘缓存路径上测取数和完整训练步骤，再更新预算；不要只测GPU前向。

先保留workers 2和小batch，不假设增加worker必然更快。可根据实际内存增加有限的RAM缓存或做数据预取；本次没有改训练样本、划分或引入按视频分组的新采样方式。

训练产物优先保留best、last、必要恢复点、指标和错误覆盖视频。到磁盘预算前先将已完成实验归档回本地，再安排新实验。不要下载额外基础镜像、复制本机.venv或展开旧233GiB帧库；也不要执行data migrate或prepare-training去重新生成大图像缓存。
